# 후보 목록 5단계 판정 엔진: 코드 구현 마스터 프롬프트

> 역할: 당신은 `code_runner/` 담당 구현자다. 보고서 파서가 넘긴 표·Claim 후보와 승인된 분석 코드의 재실행 출력 후보를 근거 기반으로 대조하는 **후보 판정 엔진**을 구현한다. 화면을 만들지 말고, 화면이 그대로 표시할 수 있는 구조화된 결과만 반환한다. 분석 언어는 Python으로 한정하지 않으며 Python, R, C/C++, Stata, Julia, SAS, MATLAB, SQL, 노트북 등에서 공통으로 동작해야 한다.

## 0. 목표와 범위

한 보고서 Claim에 코드 출력 후보가 여러 개일 수 있다. 엔진은 숫자가 비슷하다는 이유로 하나를 고르거나, 하나의 결과만 남겨 나머지 후보를 숨기면 안 된다.

각 Claim마다 다음을 모두 반환한다.

1. 생성된 후보 전체와 각 후보가 생성된 근거
2. 후보별 의미·단위·실행·허용오차 판정 내역
3. 최종 5단계 상태와 그 상태가 선택된 우선순위 근거
4. 자동 선택한 후보 또는 자동 선택하지 않은 이유
5. 사람이 다음에 확인할 정확한 위치

### 변경 범위

- 수정 가능: `code_runner/`만
- 수정 금지: `main`, `doc_parser/`, 외부 파트 폴더
- 기존 `workflow.evaluate()`와 `comparison.compare_evidence()`의 값 비교 게이트를 복제하지 말고 재사용한다.
- LLM의 추론, 변수명, 값 근접성은 후보 생성 보조 근거일 뿐 자동 확정 근거가 아니다.
- 판정 엔진의 내부 계약은 언어 중립 JSON/DTO로 둔다. 특정 언어의 AST·클래스·예외 형식이 공통 계약 밖으로 새어 나오면 안 된다.

## 1. 최종 상태는 반드시 5개로 정규화한다

실행 실패·Docker 불가·출력 누락 같은 기술 상태는 별도 최종 상태를 늘리지 않는다. 아래 5개 중 하나를 `decision_status`로 반환하고, 기술 원인은 `reason_codes`와 `system_state`에 보존한다.

| `decision_status` | 언제 부여하는가 | 절대 하면 안 되는 일 |
|---|---|---|
| `match` | 의미·연결·실행 근거가 모두 통과했고 지표별 정책 허용오차 이내 | 값만 같다고 부여 |
| `mismatch` | 의미·연결·실행 근거가 모두 통과했지만 허용오차 밖 | 의미 불일치나 실행 실패를 불일치로 부름 |
| `not_comparable` | 지표/집계/기간/대상/분모/필터/결측/가중치/단위 중 하나가 명백히 다름 | 차이를 계산하거나 0 차이를 표기 |
| `evidence_incomplete` | 승인 코드·입력·실행·출력·정책 근거가 누락되었거나 실행을 완료하지 못함 | 부족한 근거를 추측해 채움 |
| `needs_human_review` | 후보가 동점/근접하거나 의미 필드가 `unknown`, 혹은 안전한 자동 선택 조건을 충족하지 못함 | 임의 순서의 첫 후보 선택 |

`system_state`는 `completed`, `not_started`, `failed`, `isolation_unavailable`처럼 기술 상태를 담는다. 즉 `failed`는 최종 판정 `evidence_incomplete`의 원인일 수 있지만 `mismatch`가 아니다.

## 2. 언어 중립 후보 입력 계약

파서/실행 어댑터가 아래 두 컬렉션을 전달한다고 가정한다. 실제 파일 파싱이나 Docker 실행은 여기서 구현하지 않는다.

```json
{
  "provenance_id": "prov-07",
  "language": "r",
  "run_id": "run-2026-01",
  "output_value": {"amount": "15.02", "unit": "%"},
  "coordinate": {"panel": "응답자", "row_key": "서울", "column_path": ["평균 만족도"]},
  "semantics": {"metric": "만족도", "formula": "mean(score)", "period": "2025"},
  "code_locator": {"path": "analysis/main.R", "start_line": 81, "end_line": 87, "symbol": "seoul_mean"},
  "output_locator": "outputs/summary.json#/rows/seoul/mean_satisfaction",
  "execution": {"state": "completed", "contract_complete": true, "isolation": "available"}
}
```

`ClaimCandidate`도 같은 원칙으로 `claim_id`, 표 좌표, 원문값·단위, 의미 계약, 보고서 위치, 허용오차 정책을 JSON으로 전달한다. 엔진 구현 언어가 Python이어도 위 JSON을 내부 DTO로 한 번 변환한 뒤에만 판정한다.

### 2-1. 언어별 어댑터는 후보만 만들고 판정하지 않는다

```text
Python/R/C/C++/Stata/Julia/SAS/MATLAB/SQL/Notebook 어댑터
  → 정적 분석·승인 실행·출력 수집
  → 공통 ProvenanceCandidate JSON 생성
  → 공통 후보 판정 엔진 호출
```

| 언어/형식 | 어댑터가 수집할 근거 | 수집 불가 시 처리 |
|---|---|---|
| Python, R, Julia, MATLAB | 파일·함수·줄 범위, 데이터 읽기, 집계식, 출력 객체/파일 경로 | 필드 `unknown`, 자동 일치 금지 |
| C/C++ | 소스 파일·함수·줄 범위, 빌드 명령/해시, 실행 인자, stdout·출력 파일 locator | 컴파일/실행 실패는 `evidence_incomplete` |
| Stata/SAS | `.do`/`.sas` 명령 범위, 데이터 경로, `collapse`/`summarize`/출력 명령, 로그·결과 파일 | 명령 의미를 증명 못 하면 `unknown` |
| SQL | 쿼리 파일/블록, 연결된 입력 스냅샷, `GROUP BY`/집계/WHERE, 결과 테이블·행 locator | DB·스냅샷 근거 없으면 `evidence_incomplete` |
| Jupyter/RMarkdown/Quarto | 셀 ID·실행 순서·언어 커널, 셀 출력/생성 파일 locator | 실행 순서 또는 커널 근거 없으면 `needs_human_review` |

언어별 어댑터는 `mean`, `avg`, `collapse`, `SUM`, C 함수명 등을 사실로 추정하지 않는다. 실제 명령/AST/실행 로그/출력 경로로 확인한 정보만 `exact`로 채운다.

`QuantitySemantics`에는 최소한 아래 필드를 `exact`/`mismatch`/`unknown`으로 비교할 수 있게 보관한다.

```text
metric, aggregation_or_formula, period, population, denominator,
filters, missing_value_policy, weight, unit, transformation
```

각 필드는 단순 문자열뿐 아니라 원문 근거 위치를 가져야 한다. `mean(score)`와 `sum(score)`를 같은 `formula`로 정규화하면 안 된다.

## 3. 후보 생성과 후보 간 구분

### 3-1. 후보 생성 하드 조건

아래 중 하나라도 근거가 있는 경우에만 후보를 만든다.

- 같은 표 제목/표 ID 또는 행·열 좌표
- 같은 출력 키/열 이름/코드 산식의 지표 연결
- 같은 기간·대상·필터 표현
- 같은 보고서 위치와 코드 출력 locator의 명시적 연결

숫자 값 동일, `avg`/`total` 같은 변수명, 문자열 일부 유사성만으로 후보를 만들지 않는다. 반대로 값이 달라도 지표·출력 위치 근거가 강하면 후보로 남긴다. 불일치를 탐지해야 하기 때문이다.

### 3-2. 후보별 근거 벡터

모든 후보에 다음을 남긴다. 점수만 남기지 말고 어떤 항목이 후보 간 차이를 만들었는지 남겨야 한다.

```json
{
  "candidate_id": "prov-07",
  "candidate_generation_reasons": ["TABLE_ID_MATCH", "ROW_KEY_MATCH"],
  "semantic_checks": {
    "metric": {"state": "exact", "report_locator": "표 3", "code_locator": "analysis.py:81"},
    "formula": {"state": "mismatch", "report": "mean(score)", "code": "sum(score)"},
    "period": {"state": "exact"},
    "population": {"state": "exact"},
    "denominator": {"state": "mismatch", "report": "유효 응답자", "code": null}
  },
  "score_breakdown": {
    "table_coordinate": 20,
    "metric_output_key": 25,
    "period_population_filter": 20,
    "formula_denominator": -50
  }
}
```

점수는 후보 정렬을 위한 설명값이다. `match`/`mismatch`를 결정하지 않는다.

### 3-3. 동점과 상위 후보

- 후보는 점수 내림차순, 동점이면 `provenance_id` 오름차순으로 정렬해 결과를 결정적으로 만든다.
- 최고 후보와 2위 후보의 점수 차이가 설정된 `ambiguity_margin` 미만이면 자동 선택하지 않는다.
- 모든 후보를 `candidate_assessments`에 보존한다. UI가 상위 5개만 보여도 엔진은 후보 수·생략 수를 명시한다.
- `not_comparable` 후보가 있더라도 직접 출력이며 모든 의미 필드가 `exact`인 대체 후보를 제한적으로 재탐색할 수 있다. 최초 후보의 이력은 절대 삭제하지 않는다.

## 4. 판정 순서: 상태가 섞이지 않게 하는 우선순위

후보 하나를 아래 순서로 판정한다. 앞 단계에서 확정되면 뒤 단계의 값 비교는 수행하지 않는다.

```text
1. 실행 계약·코드·입력·출력·정책 근거가 있는가?
   아니오 → evidence_incomplete

2. metric/formula/period/population/denominator/filter/missing/weight/unit 중
   명백한 mismatch가 있는가?
   예 → not_comparable

3. mismatch는 없지만 unknown, 낮은 연결 신뢰도, 동점 후보가 있는가?
   예 → needs_human_review

4. 승인된 source reproduction 실행이 completed인가?
   아니오 → evidence_incomplete

5. 지표별 TolerancePolicy가 있는가?
   아니오 → needs_human_review (TOLERANCE_POLICY_MISSING)

6. 단위 환산 → 보고서 표기 자릿수 반올림 → 절대/상대 허용오차를 적용한다.
   이내 → match / 초과 → mismatch
```

### 반드시 지킬 예시

| 보고서 | 코드 후보 | 최종 상태 | 핵심 이유 |
|---|---|---|---|
| 평균 15 | 합계 15 | `not_comparable` | 값이 같아도 산식·분모 불일치 |
| 2025년 평균 15 | 2024년 평균 15 | `not_comparable` | 기간 불일치 |
| 15% | 15명 | `not_comparable` | 단위 차원 불일치 |
| 평균 15 | 평균 15.2, 0.1%p 정책 | `mismatch` | 의미는 같고 정책만 초과 |
| 평균 15 | 평균 15.02, 0.1%p 정책 | `match` | 의미 통과 + 정책 이내 |
| 일반 지수 15 | 일반 지수 15.02, 정책 없음 | `needs_human_review` | 공통 기본 오차를 임의 적용 금지 |
| 평균 15 | 실행 실패 | `evidence_incomplete` | 실패는 불일치가 아님 |

## 5. 허용오차 정책

`TolerancePolicy`는 수치마다 적용 이유를 설명해야 한다.

```json
{
  "policy_id": "report.table-3.precision",
  "metric_family": "body_weight",
  "absolute": "0.2",
  "relative": null,
  "rounding_digits": 1,
  "source": "report_declared",
  "source_locator": "표 3 각주",
  "rationale": "체중은 0.2kg 이내 재현 차이를 허용"
}
```

우선순위는 `report_declared` > `approved_metric_catalog` > 정책 없음이다. 정책 없음은 안전한 기본값 0을 뜻하지 않는다. 카탈로그 예시는 신장 `0.5cm`, 체중 `0.2kg`, 비율 `0.1%p`, 정수 건수 `0`이며, 금액·일반 지수는 보고서 선언 근거 없이는 자동 판정하지 않는다.

## 6. 반환 계약

```json
{
  "claim_id": "claim-table3-seoul",
  "final": {
    "decision_status": "mismatch",
    "selected_candidate_id": "prov-mean-seoul",
    "reason_codes": ["VALUE_OUTSIDE_TOLERANCE"],
    "reason_summary": "산식·기간·대상·분모가 일치하지만 0.2kg 허용오차를 0.1kg 초과했습니다.",
    "next_action": "보고서 표 3 각주와 outputs/summary.json#/seoul/weight를 확인하세요.",
    "tolerance_policy": {"policy_id": "report.table-3.precision"}
  },
  "candidate_assessments": [],
  "unselected_candidate_count": 0,
  "recovery_history": []
}
```

`reason_summary`는 사람이 읽을 문장이고, `reason_codes`는 기계가 분류할 안정된 코드다. `not_comparable`, `evidence_incomplete`, `needs_human_review`에서는 `absolute_difference`, `relative_difference`를 `null`로 둔다.

## 7. 구현 테스트 필수 목록

1. 값은 같지만 평균/합계가 달라 `not_comparable`
2. 기간 mismatch + 실행 실패에서도 `not_comparable` 우선
3. 의미 exact + 실행 실패는 `evidence_incomplete`
4. 의미 unknown은 `needs_human_review`
5. 1·2위 후보 점수 차이가 margin 미만이면 `needs_human_review`, 두 후보 근거 보존
6. 강한 의미 근거가 있는 값 차이 후보가 선택되어 `mismatch`
7. 신장 0.4cm 차이와 체중 0.4kg 차이가 서로 다른 정책 결과
8. 보고서 선언 정책이 카탈로그보다 우선
9. 금액/일반 지수에 정책이 없으면 자동 `match` 금지
10. `%`/ratio, `cm`/m, `kg`/g 단위 환산 후 비교
11. 코드 출력 셀 누락과 코드 전용 셀 모두 결과에서 보존
12. 자동 복구가 직접 평균 출력 후보를 찾으면 최초 합계 후보 이력 보존
13. 대체 후보의 필터/가중치가 다르면 자동 복구 금지
14. 모든 결과에 `reason_codes`, 위치, 적용 정책 또는 정책 부재 이유 존재
15. 같은 `ProvenanceCandidate` JSON을 Python/R/C 어댑터가 만들었을 때 판정 엔진 결과가 언어명과 무관하게 동일
16. R `mean(score)`, SQL `AVG(score)`, Stata `summarize score`, C/C++에서 명시적으로 계산한 평균은 공통 `formula_canonical=mean(score)`으로 변환 가능하되, 원래 언어·코드 위치도 보존
17. C/C++ 빌드 실패, R 패키지 누락, Stata 로그 미생성은 각각 `mismatch`가 아닌 `evidence_incomplete`와 언어별 원인 코드

## 8. 완료 조건

- 후보 목록 전체가 삭제되지 않고 결과에 남는다.
- 5개 상태 각각이 서로 배타적 우선순위로 결정된다.
- 후보별로 “왜 이 후보인지”, “왜 선택/탈락했는지”, “무엇이 다른지”를 구조화해 반환한다.
- 기존 scalar/triple/table 회귀 테스트와 새 후보 상태 테스트가 모두 통과한다.
- API/UI는 이 결과를 표시만 하며 판정 로직을 재계산하지 않는다.
- 새 언어를 추가할 때는 판정 엔진을 고치지 않고 `언어 어댑터 → 공통 ProvenanceCandidate` 변환만 추가한다.
