# 두 표 대조 5단계 판정 엔진 구현 명세

> 범위: 이 문서는 **보고서에서 파싱된 표**와 **승인 코드 재실행에서 생성된 표** 두 개를 대조하는 `code_runner` 담당 구현 명세다. 문서 파싱, 코드 실행, 웹 화면은 다른 파트의 책임이며 여기서는 이미 구조화된 두 표를 입력으로 받는다.

## 1. 한 문장 정의

두 표 대조는 같은 위치의 숫자를 빼는 작업이 아니다. **보고서 셀과 코드 실행 셀이 같은 연구 질문·같은 계산·같은 단위인지 증명한 뒤에만 지표별 허용오차로 값을 판단하고, 연결되지 않은 추가·누락 셀도 모두 보존하는 작업**이다.

## 2. 입력과 출력의 경계

```text
보고서 파서
  → ReportTableArtifact[]

코드 실행 어댑터 (Python/R/C/C++/Stata/SQL 등)
  → ExecutionTableArtifact[]

표 대조 엔진 (우리 파트)
  → TableReconciliationResult
       ├─ 표 연결 결과
       ├─ 셀 연결 결과
       ├─ 추가/누락 셀 목록
       ├─ 후보별 근거와 탈락 사유
       └─ 각 연결 셀의 5단계 최종 판정
```

엔진은 “업로드 파일을 읽었다”, “코드를 실제 실행했다”라고 주장하지 않는다. 입력 artifact의 `source_locator`, `code_locator`, `output_locator`, 실행 계약을 그대로 감사 기록으로 전달한다.

## 3. 표와 셀의 최소 공통 계약

언어와 표 형식이 달라도 아래 공통 구조로 정규화한다.

```json
{
  "table_id": "report-table-3",
  "title": "2025년 지역별 평균 만족도",
  "cells": [
    {
      "coordinate": {
        "panel": "전체 응답자",
        "row_key": "서울",
        "column_path": ["만족도", "평균"]
      },
      "value": {"amount": "15.0", "unit": "%"},
      "raw_value": "15.0%",
      "semantics": {
        "metric": "만족도",
        "formula": "mean(score)",
        "period": "2025년",
        "population": "서울 응답자",
        "denominator": "유효 응답자",
        "filters": ["region=seoul"],
        "missing_value_policy": "exclude_missing",
        "weight": null,
        "transformation": null
      },
      "source_locator": "보고서 12쪽 표 3, 서울 행, 평균 열",
      "tolerance_policy": "report.table3.rate.v1"
    }
  ]
}
```

`column_path`는 다단 헤더를 순서대로 저장한다. 예를 들어 `만족도 > 평균`, `남성 > 20대 > 평균`을 단일 문자열로 평탄화하지 않는다.

## 4. 표 연결: 어떤 표끼리 대조할지

표 연결은 셀의 최종 판정과 분리한다. `표 3`과 `코드 출력 3`처럼 번호가 같다는 사실만으로 연결하지 않는다.

### 4-1. 표 후보 생성 근거

보고서 표와 실행 표의 쌍마다 아래 근거를 수집한다.

| 근거 | 예시 | 역할 |
|---|---|---|
| 표 ID 또는 명시적 mapping | `표 3` ↔ `summary_table` | 강한 연결 근거 |
| 제목의 정규화 토큰 | `지역별 만족도` ↔ `만족도 지역 요약` | 보조 근거 |
| 공통 행·열 좌표 | `서울 / 만족도 > 평균` | 구조 근거 |
| 대표 셀의 지표·기간 | `2025년 서울 만족도` | 의미 근거 |
| 코드 출력 locator·주석 | `# Table 3 reproduction` | 감사 근거 |

값이 우연히 같은 셀 수는 표 후보 생성 점수에 넣지 않는다.

### 4-2. 표 연결 결과

| 결과 | 의미 | 이후 처리 |
|---|---|---|
| `matched` | 최고 후보가 명확하고 최소 연결 근거 충족 | 셀 정렬 진행 |
| `ambiguous` | 최고·차순위 표 후보가 동점 또는 margin 미만 | 셀 값 비교 금지, 후보 목록 보존 |
| `report_only_table` | 보고서 표에 실행 표 후보 없음 | 모든 보고서 셀을 누락 목록에 기록 |
| `execution_only_table` | 실행 표가 어느 보고서 표에도 연결되지 않음 | 추가 지표 표로 기록 |

같은 실행 표를 여러 보고서 표에 자동 중복 연결하지 않는다. 1:1 연결이 불확실하면 `ambiguous`다.

## 5. 셀 정렬: 행·열·추가 지표를 숨기지 않는다

연결된 두 표 안에서 셀 키를 아래처럼 만든다.

```text
normalized(panel) + normalized(row_key) + normalized(column_path[])
```

정규화는 대소문자·불필요 공백·명시된 동의어만 처리한다. `평균`과 `합계`, `2024`와 `2025`, `서울`과 `서울시 전체`를 자동 동치로 만들지 않는다.

셀 정렬 결과는 최종 5단계 상태와 별도로 유지한다.

| `relation` | 보고서 셀 | 실행 셀 | 의미 |
|---|---|---|---|
| `matched_cell` | 있음 | 있음 | 의미·값 판정 가능 후보 |
| `report_only_cell` | 있음 | 없음 | 실행 출력 누락 또는 연결 실패 후보 |
| `execution_only_cell` | 없음 | 있음 | 코드가 만든 추가 지표, 불일치로 단정 금지 |
| `ambiguous_cell` | 있음 | 여러 개 | 후보 경합, 임의 선택 금지 |

`report_only_cell`과 `execution_only_cell`은 숫자 차이를 계산하지 않는다. 두 경우는 각각 `MISSING_EXECUTION_COUNTERPART`, `NO_REPORT_COUNTERPART` 같은 원인 코드와 locator를 남긴다.

## 6. 의미 대조: 값 비교 전에 10개 필드를 본다

`matched_cell`일 때만 아래 필드를 각각 `exact`, `mismatch`, `unknown`으로 대조한다.

| 필드 | 질문 | `mismatch` 예시 |
|---|---|---|
| metric | 무엇을 재는가? | 만족도 vs 소득 |
| aggregation/formula | 어떻게 계산했는가? | `mean(score)` vs `sum(score)` |
| period | 어느 시점/기간인가? | 2025년 vs 2024년 |
| population | 누구/무엇이 대상인가? | 서울 응답자 vs 전체 응답자 |
| denominator | 평균·비율의 분모는 무엇인가? | 유효 응답자 vs 전체 응답자 |
| filters | 어떤 조건을 제외/선택했는가? | 여성만 vs 전체 |
| missing value | 결측을 어떻게 처리했는가? | 제외 vs 0 대체 |
| weight | 가중치를 썼는가? | 가중평균 vs 단순평균 |
| transformation | 로그·표준화·환산이 있는가? | 원값 vs 로그값 |
| unit | 표현 차원이 같은가? | `%` vs 명, kg vs cm |

각 항목은 상태만 남기지 말고 보고서 근거 위치, 코드 근거 위치, 양쪽 원문값을 남긴다.

```json
{
  "field": "aggregation/formula",
  "state": "mismatch",
  "report_value": "mean(score)",
  "execution_value": "sum(score)",
  "report_locator": "보고서 12쪽 표 3 각주",
  "execution_locator": "analysis/main.R:81-87"
}
```

## 7. 핵심: 5단계 최종 판정 우선순위

다섯 상태는 서로 섞이면 안 된다. 아래 순서가 절대 우선순위다.

```text
0. 셀이 단일하게 연결되었는가?
   아니오 → needs_human_review

1. 실행 계약·입력 해시·코드 근거·실행 결과·출력 위치가 충분한가?
   아니오 → evidence_incomplete

2. 의미 필드 중 하나라도 mismatch인가?
   예 → not_comparable

3. 의미 mismatch는 없지만 unknown이 있거나 후보 연결 신뢰도가 낮은가?
   예 → needs_human_review

4. 적용 가능한 허용오차 정책이 있는가?
   아니오 → needs_human_review

5. 단위 환산 → 보고서 자릿수 반올림 → 절대/상대 허용오차 비교
   이내 → match
   초과 → mismatch
```

### 상태별 정확한 구분

| 상태 | 필요조건 | 금지되는 오해 |
|---|---|---|
| `match` | 의미 모두 exact, 단일 연결, 실행 근거 충족, 정책 이내 | “문자열 숫자가 같다” |
| `mismatch` | `match`와 같은 근거 조건 + 정책 초과 | “실행 실패했다” |
| `not_comparable` | 의미/단위의 명백한 mismatch | “숫자 차이가 크다” |
| `evidence_incomplete` | 입력·코드·실행·출력·정책의 필수 근거 누락 | “의미가 다르다” |
| `needs_human_review` | unknown, 후보 경합, 정책 부재, 연결 불확실 | “자동 판정 실패” |

예를 들어 `기간 mismatch + 실행 실패`라면 “같은 연구 질문이 아니다”가 더 강한 사실이므로 `not_comparable`이다. 반대로 의미는 같지만 Docker 실행이 실패하면 `evidence_incomplete`이며 `mismatch`가 아니다.

## 8. 지표별 허용오차 정책

허용오차는 하나의 전역 상수가 아니다. 보고서 셀마다 `TolerancePolicy`를 연결한다.

| 우선순위 | 정책 출처 | 적용 예 |
|---:|---|---|
| 1 | `report_declared` | 보고서 각주/분석계획의 명시된 재현 오차 |
| 2 | `approved_metric_catalog` | 신장 `0.5cm`, 체중 `0.2kg`, 비율 `0.1%p`, 정수 건수 `0` |
| 3 | 없음 | 자동 `match`/`mismatch` 금지, `needs_human_review` |

정책에는 `policy_id`, 절대·상대 허용오차, 허용오차 기준 단위, 반올림 자릿수, 근거 위치, 설명을 저장한다. 금액·종합지수처럼 연구별 정의가 크게 달라지는 지표에는 기본 정책을 임의 적용하지 않는다.

## 9. 후보가 5개 이상일 때 보존 방식

후보가 다섯 개인 것과 최종 상태가 다섯 개인 것은 다른 개념이다.

```text
Claim 1개
  ├─ 후보 A: 공식·기간 exact, 0.02 차이 → match
  ├─ 후보 B: formula mismatch → not_comparable
  ├─ 후보 C: period mismatch → not_comparable
  ├─ 후보 D: 실행 로그 없음 → evidence_incomplete
  └─ 후보 E: 의미 일부 unknown → needs_human_review

최종 선택: 후보 A
나머지: 탈락 사유와 근거를 삭제하지 않고 candidate_assessments에 보존
```

자동 선택은 후보 A가 단일 최고 후보이고, 모든 의미 필드가 `exact`이며, 실행 근거와 허용오차 정책이 있을 때만 가능하다. 최고·차순위 후보가 근접하면 최종 상태는 `needs_human_review`이고 후보 A를 임의 확정하지 않는다.

## 11. 구현 의사코드

```text
for each report_table:
    table_candidates = find_table_candidates(report_table, execution_tables)
    table_relation = resolve_table_relation(table_candidates)

    if table_relation is not matched:
        preserve_table_candidates_and_unmatched_cells()
        continue

    for each report_cell in report_table:
        execution_candidates = align_by_coordinate(report_cell, matched_execution_table)
        relation = resolve_cell_relation(execution_candidates)

        if relation is not matched_cell:
            preserve_relation_with_locator()
            continue

        semantic_checks = compare_semantics(report_cell, execution_cell)
        decision = decide_by_precedence(
            relation,
            execution_contract,
            semantic_checks,
            tolerance_policy,
            normalized_values
        )
        preserve_decision_and_all_evidence()

    preserve_execution_only_cells()
```

언어별 코드 분석기는 `ExecutionTableArtifact`를 만들기만 한다. 후보 생성·의미 비교·5단계 판정은 모든 언어에 공통인 이 엔진에서 한 번만 수행한다.

## 12. 필수 테스트

1. 행·열 순서가 달라도 같은 좌표면 연결
2. 평균 15와 합계 15는 `not_comparable`
3. 같은 의미지만 허용오차 초과는 `mismatch`
4. `%`와 ratio, cm와 m, kg와 g는 환산 뒤 대조
5. 보고서 선언 정책이 카탈로그보다 우선
6. 일반 지수/금액에 정책이 없으면 `needs_human_review`
7. 실행 표에 없는 보고서 셀은 `report_only_cell`
8. 보고서에 없는 실행 지표는 `execution_only_cell`
9. 동일 좌표 실행 셀이 둘이면 `ambiguous_cell`
10. 후보 1·2위 점수 차이가 작으면 자동 선택 금지
11. 의미 mismatch + 실행 실패는 `not_comparable` 우선
12. 의미 exact + 실행 실패는 `evidence_incomplete`
13. Python/R/C/C++/Stata/SQL 어댑터가 같은 공통 artifact를 만들면 판정 결과도 동일
14. 모든 결과 행에 reason code, 사람이 읽을 설명, 보고서/코드/출력 위치가 존재

## 코드 생성 요청문

아래 요청문을 구현 담당 AI에게 그대로 전달한다.

```text
code_runner/에 두 표 대조 5단계 판정 엔진을 구현하라.

입력은 파서가 만든 ReportTableArtifact 목록과 승인 코드 실행 어댑터가 만든 ExecutionTableArtifact 목록이다. Python/R/C/C++/Stata/SQL 등 언어별 어댑터는 공통 artifact를 만들기만 하고, 판정 엔진은 언어 중립적으로 한 번만 구현한다.

반드시 다음을 구현한다.
1. 표 후보 연결: 표 ID/제목/행열 구조/의미 근거를 보존하고 ambiguous/report_only/execution_only를 구분한다.
2. 셀 정렬: panel + row_key + column_path를 키로 하며 matched_cell/report_only_cell/execution_only_cell/ambiguous_cell을 보존한다.
3. 의미 대조: metric, formula, period, population, denominator, filters, missing value, weight, transformation, unit을 exact/mismatch/unknown과 locator로 반환한다.
4. 최종 상태는 match, mismatch, not_comparable, evidence_incomplete, needs_human_review 다섯 개로 정규화한다. 상태 우선순위는 구현 명세 7절을 정확히 따른다.
5. 허용오차는 셀별 TolerancePolicy를 사용한다. report_declared > approved_metric_catalog > 정책 없음 순이며 정책 없음에서는 자동 match/mismatch를 만들지 않는다.
```
