# 숫자내력 재실행·대조 통합 구현 명세

> 대상: 팀 LINK의 `code_runner/` 담당자와 `app/` 연동 담당자
>
> 목표: 보고서에 적힌 숫자를 **특정 코드·특정 입력·특정 실행 결과**와 근거 있게 연결하고, 재실행 결과를 사람이 검토할 수 있는 형태로 반환한다.

---

## 1. 문제와 우리 파트의 역할

연구·사업 보고서에는 `87.5%`, `2.7배`, `3.5억원`처럼 중요한 결과 수치가 있다. 그러나 보통 다음 질문에 바로 답하기 어렵다.

> “이 숫자는 어느 데이터의 어떤 산식으로 나왔고, 지금 다시 돌리면 같은가?”

숫자내력은 이 질문을 위한 **제출 전 검토 도구**다. 수치를 새로 만들어 주거나 연구 결과를 자동 확정하지 않는다. 이미 있는 보고서 수치와 실행 근거를 연결해, 사람이 확인할 수 있는 검토표를 만든다.

`code_runner/`의 책임은 아래로 한정한다.

```text
승인된 코드·입력·실행 계약 수신
            ↓
안전한 격리 환경 검증
            ↓
승인된 코드만 재실행
            ↓
출력값·실행 메타데이터 수집
            ↓
의미 조건과 수치 조건을 대조
            ↓
상태·근거·원인 후보를 JSON으로 반환
```

### 다른 파트와의 경계

| 폴더 | 담당 | `code_runner`가 하는 일 | 하지 않는 일 |
|---|---|---|---|
| `doc_parser/` | 문서·수치 | Claim JSON을 입력으로 받음 | HWPX/PDF/DOCX 파싱 수정·구현 |
| `code_runner/` | 코드·실행 | 이 문서의 모든 기능 | UI 화면 구현 |
| `app/` | Streamlit 검증표 | 결과 JSON을 표시 | 실행 결과를 임의로 해석·수정 |
| `data/samples/` | 공개 데모 자료 | 읽기 전용 입력으로 참조 | 원본 데이터를 실행 중 수정 |

## 2. 핵심 원칙: 값 비교 전에 의미를 먼저 대조한다

보고서가 `2.7배`, 재실행 결과가 `2.41배`라고 해서 곧바로 “불일치”라고 하면 안 된다. 둘이 같은 질문에 대한 수치라는 증거가 먼저 필요하다.

```text
보고서 Claim
  └─ 지표 / 단위 / 기간 / 대상 / 분모 / 산식 의미
             ↓
Trace(연결 근거)
  └─ 왜 이 코드·입력·출력이 같은 수치를 뜻하는가
             ↓
실행 Evidence
  └─ 코드 버전 / 입력 식별값 / 명령 / 출력 위치 / 실제 결과
             ↓
기계적 1차 판정
             ↓
연구자 최종 확정
```

### 2-1. Claim: 보고서가 주장한 값

```json
{
  "claim_id": "C-042",
  "raw_value": "2.7배",
  "normalized_value": 2.7,
  "unit": "배",
  "metric": "처리 속도 개선 배수",
  "period": "2025년 실험",
  "population": "시험 데이터셋 A",
  "denominator": "기존 방법 평균 처리 시간",
  "location": {
    "section": "4. 연구성과",
    "page": 42,
    "source_type": "paragraph"
  },
  "source_kind": "research_result",
  "research_result": true
}
```

표·통계량·논문 예시 수치라면 `location`을 페이지 수준으로 뭉뚱그리지 않는다.
검토자가 같은 셀과 문맥을 다시 찾을 수 있게 아래 정보를 추가한다.

```json
{
  "file_sha256": "sha256:...",
  "printed_pages": [867, 868],
  "table_id": "Table 1",
  "row": "Sample 1",
  "column": "p-value",
  "cell_text": "0.004",
  "context_text": "Pearson chi-square test",
  "source_kind": "published_example",
  "research_result": false,
  "interpretation_scope": "교육용 통계 예시"
}
```

`source_kind`의 최소 값은 다음과 같다.

```text
research_result    : 실제 연구·사업 결과로 제시된 수치
published_example  : 논문·보고서가 설명을 위해 든 예시 수치
derived_summary    : 다른 표·데이터에서 요약해 적은 수치
quoted_statistic   : 외부 출처를 인용한 수치
```

### 2-2. Evidence: 재실행으로 얻은 값

```json
{
  "evidence_id": "E-042",
  "value": 2.41,
  "unit": "배",
  "script_id": "speed_benchmark_v1",
  "script_path": "analysis/speed.py",
  "code_revision": "git:abc123",
  "input_digest": "sha256:...",
  "output_location": "outputs/benchmark.json#/speedup",
  "run_id": "run-20260930-001",
  "execution_status": "completed"
}
```

### 2-3. Trace: Claim과 Evidence의 연결 근거

```json
{
  "claim_id": "C-042",
  "evidence_id": "E-042",
  "confidence": "high",
  "metric_match": "exact",
  "period_match": "exact",
  "population_match": "exact",
  "denominator_match": "exact",
  "formula_match": "exact",
  "link_reason": [
    "지표명 일치",
    "동일 시험 데이터셋",
    "동일 분모 정의",
    "코드 출력 키 일치"
  ]
}
```

**Trace가 없으면 출력값은 참고값일 뿐이다. `match` 또는 `mismatch` 판정을 만들 수 없다.**

### 2-4. Evidence 종류: 원본 재현과 독립 검산을 구분한다

“다시 계산했다”는 말은 서로 다른 세 가지 활동을 뜻할 수 있다. 화면·JSON·발표에서 이들을 같은 재현 결과로 표시하면 안 된다.

| `evidence_kind` | 정의 | 원본 `match/mismatch` 가능 여부 | 화면 표기 |
|---|---|---|---|
| `source_reproduction` | 원저자 또는 공식 코드·원자료·실행환경을 확인해 재실행 | 가능. 모든 원본 근거·Trace high·Docker 조건 충족 시만 | `원본 재현` |
| `independent_recalculation` | 공개된 표·산식을 바탕으로 별도 승인 코드로 계산 | 불가. 계산값은 보여주되 `needs_human_review` | `독립 재계산 — 원본 재현 아님` |
| `arithmetic_check` | 빈도·비율·합계 같은 산술 관계만 검산 | 불가. 계산값은 보여주되 `needs_human_review` | `산술 검산 — 원본 재현 아님` |

Evidence에는 종류뿐 아니라 원본 증명 상태를 남긴다.

```json
{
  "evidence_kind": "independent_recalculation",
  "original_code_proof": "missing",
  "original_data_proof": "missing",
  "original_execution_proof": "missing",
  "formula_proof": "paper_text_and_table",
  "disclosure": "논문 표와 본문에 제시된 빈도를 이용한 독립 재계산 결과이며, 원저자 코드·원자료 기반 재현 결과가 아닙니다."
}
```

### Evidence 종류별 판정 게이트

```text
source_reproduction
  + 원본 코드·입력·실행환경 증명
  + 승인된 실행 계약
  + Trace high / 의미 조건 exact
  + Docker 실행 성공
      → match 또는 mismatch 가능

independent_recalculation / arithmetic_check
      → 계산 결과·근거·차이 유형은 저장
      → 최종 기계 상태는 needs_human_review
      → disclosure를 화면에 반드시 표시

원본 재현을 요청했지만 원본 코드·데이터·승인 script 중 하나가 없음
      → evidence_incomplete
```

이 구분은 기능을 약하게 만드는 것이 아니라, “표의 숫자를 독립 계산했다”는 유용한 결과와
“원저자의 연구를 재현했다”는 강한 주장을 정직하게 분리하는 장치다.

## 3. 입력 계약: 실행 전에 반드시 확정할 것

실행 요청에는 Claim만이 아니라 아래 실행 계약이 포함되어야 한다.

```yaml
claim_id: C-042

script:
  id: speed_benchmark_v1
  path: analysis/speed.py
  revision: git:abc123
  approved_by_team: true

input:
  files:
    - data/samples/benchmark_a.csv
  digest: sha256:...
  read_only: true

command:
  - python
  - analysis/speed.py
  - --input
  - data/samples/benchmark_a.csv

output:
  path: outputs/benchmark.json
  locator: /speedup
  expected_unit: 배

comparison:
  absolute_tolerance: 0.05
  relative_tolerance: null
  report_rounding_digits: 1

limits:
  network: disabled
  memory: 4GB
  cpu: 1
  timeout_seconds: 300
  isolation: docker_required
```

### 실행 계약 필수 조건

| 필드 | 없을 때 상태 | 이유 |
|---|---|---|
| 승인된 `script.id` | `evidence_incomplete` | 임의 코드 실행 방지 |
| 코드 경로·버전 | `evidence_incomplete` | 어떤 계산을 재현했는지 알 수 없음 |
| 입력 파일·식별값 | `evidence_incomplete` | 데이터 버전이 불명확함 |
| 고정 실행 인자 | `evidence_incomplete` | 실행 재현 불가 |
| 출력 경로·값 위치 | `evidence_incomplete` | 어떤 결과를 읽어야 할지 불명확함 |
| Trace 의미 조건 | `needs_human_review` 또는 `not_comparable` | 같은 수치를 비교한다는 보장이 없음 |
| Docker 격리 | `isolation_unavailable` | 안전하지 않은 코드는 실행하지 않음 |

## 4. 안전한 재실행 정책

### 절대 허용하지 않는 것

- 업로드된 임의 Python, R, Notebook, shell 코드 실행
- 사용자가 입력한 명령문을 그대로 쉘에서 실행
- `shell=True` 또는 문자열로 조합한 명령 실행
- Docker가 없을 때 로컬 Python으로 조용히 우회 실행
- 원본 문서·입력 데이터 수정
- 네트워크 접근을 허용한 채 실행
- 로그에 API 키, 개인정보, 원문 전체, 입력 데이터 전체 저장

### Docker 실행 기준

```text
네트워크:   완전 차단 (`--network none`)
입력:       읽기 전용 마운트
출력:       전용 출력 폴더만 쓰기 가능
메모리:     4GB 이하
CPU:        제한 적용
시간:       300초 이내, 초과 시 강제 종료
실행 대상:  팀 allowlist의 script_id만
명령:       승인된 고정 인자 배열만
```

### 격리 환경이 없을 때의 올바른 동작

```text
Docker 점검 실패
      ↓
코드를 실행하지 않음
      ↓
status = isolation_unavailable
      ↓
화면에는 “안전한 격리 환경을 확인하지 못해 실행하지 않았습니다” 표시
```

이것은 기능 실패가 아니라 **안전하게 중단한 투명한 결과**다.

## 5. 값 정규화와 비교 규칙

### 5-1. 최소 단위 지원 범위

| 보고서 표현 | 내부 정규화 | 변환 규칙 |
|---|---:|---|
| `87.5%` | 87.5 `%` | `%` 그대로 |
| `0.875` 비율 | 87.5 `%` | 비율 × 100 |
| `2.7배` | 2.7 `배` | 그대로 |
| `3.5억원` | 350 `백만원` | 억원 × 100 |
| `3,500백만원` | 3500 `백만원` | 쉼표 제거 |
| `1,500,000원` | 1.5 `백만원` | 원 ÷ 1,000,000 |
| `1200ms` | 1.2 `s` | ms ÷ 1,000 |

`%`와 `%p`는 의미가 다르므로 자동 변환하지 않는다. 이 경우 `not_comparable` 또는 `needs_human_review`로 처리한다.

### 5-2. 반올림과 허용오차

보고서의 표기 자릿수가 낮으면 재실행 값은 더 정밀할 수 있다.

```text
보고서: 2.7배
재실행: 2.714배
보고서 자릿수: 소수 첫째 자리
2.714 → 2.7로 반올림 가능
판정: match
```

반올림 뒤에도 차이가 허용오차를 벗어나면 `mismatch`다.

```text
보고서: 2.7배
재실행: 2.41배
판정: mismatch
```

### 5-3. 반올림은 반드시 보고서 표기 단위에서 먼저 한다

보고서의 자릿수는 **정규화 단위가 아니라 보고서가 실제로 쓴 단위**의 자릿수다.
따라서 재실행 값을 보고서 단위로 변환하고 반올림한 뒤 비교해야 한다.

```text
올바른 순서
1. 실행값을 보고서 표기 단위로 변환
2. 보고서의 표기 자릿수로 실행값 반올림
3. 보고서 값과 허용오차 비교
4. 필요하면 결과 표시용 정규화 값도 별도로 저장
```

```text
잘못된 순서
실행값을 기준 단위로 정규화 → 같은 자릿수로 반올림 → 비교

이 방식은 단위 스케일이 바뀌면 자릿수 의미도 바뀌므로 금지한다.
```

| 보고서 값 | 재실행 값 | 보고서 자릿수 | 올바른 처리 | 기대 상태 |
|---|---|---:|---|---|
| `1200ms` | `1.2s` | 0 | `1.2s → 1200ms → 1200ms` | `match` |
| `1,500,000원` | `1.5백만원` | 0 | `1.5백만원 → 1,500,000원` | `match` |
| `3.5억원` | `3.54억원` | 1 | `3.54억원 → 3.5억원` | `match` |

구현 시 실행값의 정규화 기준값만 보관하지 말고 다음을 함께 보관한다.

- `report_unit`: 보고서가 쓴 원래 단위
- `report_rounding_digits`: 보고서 표기 자릿수
- `evidence_in_report_unit`: 보고서 단위로 환산한 실행값
- `rounded_evidence_in_report_unit`: 실제 비교에 사용한 반올림 값

이 네 값이 있어야 UI와 연구자가 왜 `match`가 나왔는지 재현할 수 있다.

### 5-4. p-value와 임계값 수치는 일반 허용오차로 비교하지 않는다

p-value는 작고 표시 자릿수에 민감하므로 `0.004 ± 0.005`처럼 넓은 고정 허용오차를 쓰면 안 된다.
비교 방식은 Claim마다 `comparison_mode`로 명시한다.

| `comparison_mode` | 적용 대상 | 비교 규칙 |
|---|---|---|
| `exact_value` | 원시 p-value를 동일 환경에서 재현 | 검정 방법·양측/단측·소프트웨어·버전·입력·결측 처리까지 동일해야 함 |
| `rounded_interval` | `0.004`처럼 자릿수가 정해진 표시값 | 표시 단위와 반올림 방식으로 만든 구간 안에 실행값이 있는지 확인 |
| `threshold` | `p < 0.001`, `p ≥ 0.05` | 숫자 동등 비교가 아니라 부등식 조건이 참인지 확인 |

예를 들어 `0.004`가 일반적인 소수 셋째 자리 반올림(`half_up`) 값이라면 허용 구간은
`0.0035 이상, 0.0045 미만`이다. 반올림 방식이 확인되지 않으면 경계값을 자동 확정하지 않고
`needs_human_review`로 보낸다.

```json
{
  "metric": "Pearson chi-square p-value",
  "comparison_mode": "rounded_interval",
  "report_rounding_digits": 3,
  "rounding_mode": "half_up",
  "test_method": "Pearson chi-square",
  "sidedness": "unknown",
  "expected_count_rule": "unknown"
}
```

`p < 0.001`은 정확한 `0.001` 값이 아니다. `exact_value` 또는 숫자 허용오차 비교 대상으로 바꾸지 않는다.

비교 시 결과에는 항상 아래를 남긴다.

- 보고서 원문값과 정규화 값
- 실행 원문값과 정규화 값
- 적용 단위 변환
- 반올림 자릿수
- 절대·상대 허용오차
- 절대 차이·상대 차이

## 6. 상태 체계와 판정 순서

### 상태 정의

| 상태 | 의미 | UI 핵심 문구 |
|---|---|---|
| `match` | 의미·실행 조건이 충족되고 허용오차 이내 | 재실행 결과가 보고서 표기와 일치합니다. |
| `mismatch` | 의미·실행 조건은 충족했지만 허용오차 밖 | 재실행 결과가 보고서 표기와 다릅니다. |
| `not_comparable` | 지표·기간·대상·분모·산식·단위가 달라 비교 불가 | 같은 기준의 수치인지 확인할 수 없습니다. |
| `evidence_incomplete` | 코드·입력·명령·출력 중 근거가 부족 | 재실행에 필요한 근거가 부족합니다. |
| `isolation_unavailable` | Docker 격리를 확인하지 못해 미실행 | 안전한 격리 환경이 없어 실행하지 않았습니다. |
| `execution_failed` | 격리 실행 중 오류·시간초과·출력 파싱 실패 | 실행은 시도했지만 결과를 얻지 못했습니다. |
| `needs_human_review` | 자동 연결 신뢰도가 낮거나 의미 확인 필요 | 사람이 지표 의미와 연결 근거를 확인해야 합니다. |

### 판정 순서

```text
1. Claim과 실행 계약 필수 필드가 있는가?
   └─ 아니오 → evidence_incomplete

2. Docker 격리를 안전하게 사용할 수 있는가?
   └─ 아니오 → isolation_unavailable (실행 금지)

3. 승인된 코드·입력·명령·출력 위치인가?
   └─ 아니오 → evidence_incomplete

4. 지표·기간·대상·분모·산식이 같은가?
   └─ 하나라도 명백히 불일치 → not_comparable
   └─ 명백한 불일치는 없지만 정보 부족 또는 신뢰도 낮음 → needs_human_review

5. 의미 조건이 모두 exact이고 Trace 신뢰도가 high일 때만 격리 실행 결과를 평가한다.
   └─ 오류·시간 초과·출력 없음 → execution_failed

6. Evidence 종류가 source_reproduction인가?
   └─ 아니오(independent_recalculation / arithmetic_check) → needs_human_review + disclosure

7. 단위 변환·반올림·허용오차 적용 후 같은가?
   └─ 예 → match
   └─ 아니오 → mismatch
```

### 중요한 금지 규칙

```text
실행 오류 ≠ mismatch
의미 불일치 ≠ mismatch
출력값이 우연히 같음 ≠ match
```

### 6-1. 복합 상태의 우선순위

한 요청에 여러 문제가 있어도 상태를 임의 순서로 반환하면 안 된다.

```text
필수 계약 누락                 → evidence_incomplete
Docker 격리 불가                → isolation_unavailable
명백한 의미 불일치              → not_comparable
의미 정보 부족 또는 Trace low   → needs_human_review
의미 조건 exact + 실행 실패     → execution_failed
의미 조건 exact + 실행값 비교   → match / mismatch
```

특히 다음 규칙을 지킨다.

```text
기간 불일치 + 실행 실패          → not_comparable
분모 불일치 + Trace low          → not_comparable
Trace low + 의미 조건 모두 exact → needs_human_review
```

명백한 의미 불일치는 실행 결과가 있거나 실행에 실패했는지와 무관하게
“같은 질문의 수치가 아니다”라는 사실을 먼저 알려야 한다.

### 6-2. 회귀 테스트 필수 사례

아래 사례는 상태별 기본 테스트와 별도로 반드시 자동 테스트로 유지한다.

1. `1200ms` 보고서 값과 `1.2s` 실행값은 자릿수 0·허용오차 0에서도 `match`
2. `3.5억원` 보고서 값과 `3.54억원` 실행값은 소수 첫째 자리에서 `match`
3. 기간 또는 분모 `mismatch` + `execution_failed`는 `not_comparable`
4. 기간 또는 분모 `mismatch` + Trace `low`는 `not_comparable`
5. 의미 조건이 모두 `exact` + Trace `low`는 `needs_human_review`

`match`와 `mismatch`는 Trace 신뢰도 `high`이며 지표·기간·대상·분모·산식이 모두 검증됐을 때만 만들 수 있다.

## 8. MVP 데모 시나리오

해커톤에서는 기능을 넓히기보다, 하나의 입력 묶음이 끝까지 흐르는 모습을 보여주는 것이 중요하다.

### 데모 입력 묶음

```text
보고서: 공개 가능한 한국어 보고서의 한 문장 또는 표
Claim: “시험 데이터셋 A에서 처리 속도가 기존 대비 2.7배 향상되었다.”
입력: data/samples/benchmark_a.csv
코드: 팀이 검토한 고정 분석 스크립트 1개
출력: outputs/benchmark.json 의 speedup 값
```

### 꼭 확보할 결과 2건

| 사례 | 보고서 값 | 재실행 값 | 기대 상태 | 발표에서 말할 점 |
|---|---:|---:|---|---|
| 반올림 일치 | `87.5%` | `0.875` | `match` | 단위 변환·반올림을 근거와 함께 처리 |
| 의도적 불일치 | `2.7배` | `2.41배` | `mismatch` | 숫자만 비교하지 않고 코드·입력·출력을 남김 |

추가로 Docker가 없는 환경에서는 `isolation_unavailable` 결과를 한 건 보여주면, 안전 정책을 과장 없이 설명할 수 있다.

## 9. 구현 우선순위

### 지금 반드시 만들 것

1. Claim·Execution Contract·Review Result JSON 타입/검증
2. 승인된 script allowlist
3. Docker 사전 점검과 안전 옵션 적용
4. 출력 JSON에서 값 추출
5. 단위 정규화·반올림·허용오차 비교
6. 상태별 JSON 반환
7. `match`·`mismatch`·`isolation_unavailable` 데모 근거 확보

### 시간이 남으면 만들 것

- 더 많은 단위와 Excel 수식 근거 연결
- 코드 파일·라인 후보 검색 강화
- 실행 로그 요약과 재시도 기록
- 사람이 확정한 결과의 내력 파일 저장

### 이번 MVP에서 하지 않을 것

- 임의 사용자 코드 실행
- 실제 비공개 연구 데이터 처리
- 그래프 이미지 속 숫자 OCR 자동 확정
- LLM이 숫자·근거·최종 판정을 생성하는 기능
- 인증, 사용자 계정, 협업 권한 시스템

## 10. 완료 기준 체크리스트

### 기능

- [ ] 승인된 스크립트가 아니면 실행하지 않는다.
- [ ] Docker를 확인할 수 없으면 로컬 실행하지 않고 `isolation_unavailable`을 반환한다.
- [ ] 성공 실행에서 코드·입력·출력 위치·실행 시간·결과값을 남긴다.
- [ ] 의미 조건이 부족하면 `match`나 `mismatch`를 만들지 않는다.
- [ ] 단위·반올림·허용오차를 결과에 투명하게 남긴다.
- [ ] 실행 오류는 `execution_failed`로 분리한다.

### 데모·발표

- [ ] 일치 사례와 불일치 사례가 모두 있다.
- [ ] 불일치 사례에서 “어느 보고서 위치, 어느 코드, 어느 입력, 어느 출력”인지 보인다.
- [ ] 원인 후보가 확정 사실처럼 표시되지 않는다.
- [ ] 최종 확정이 사람에게 남아 있다.

### 저장소 규칙

- [ ] 변경은 `code_runner/` 안에 한정한다.
- [ ] 새 라이브러리·모델·외부 데이터를 추가했다면 `docs/USED.md` 기록 필요 여부를 팀에 알린다.
- [ ] `.env`, 키, 개인정보, 실제 민감 데이터가 포함되지 않았다.
